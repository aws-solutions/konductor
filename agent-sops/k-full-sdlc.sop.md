# Full SDLC

## Overview

This SOP takes a project or feature through the full lifecycle: codebase analysis, requirements, design, principal engineer review, feature splitting, per-feature specs, implementation, code review, test coverage, and documentation. Each phase delegates to an existing SOP where one covers the work, or spawns a specialist agent where none does. Every phase is skippable and gated.

Invoked when the engineer asks to build something end to end (e.g., "Build X", "Take Y from requirements through tests"). For a single phase, run that phase's SOP directly.

The implementation guide document format is out of scope — this SOP produces a README and developer guide, not a separately-published guide artifact.

This is not the same SOP as the similarly-named full SDLC pass SOP in the internal extension package, which adds an earlier investment-validation phase and additional internal-tooling handoffs this package does not have.

## Parameters

- **project_description** (required): The project or feature to build.
- **codebase_path** (optional, default: current directory): Existing codebase to build into. Drives Step 1. **A resumed invocation MUST pass `codebase_path` explicitly, matching the value used when the session was minted.** The default (current working directory) is resolved fresh on every invocation — a resume launched from a different working directory computes a different default, and therefore a different `project_signature` (see Progress Tracking), even after that signature's `codebase_path` component is canonicalized to remove symlink/mount-alias divergence: canonicalization only resolves aliases of the same directory, it does not make two genuinely different working directories equal. The result is a silently minted new session rather than a resumed one. If the `sop-state-management` skill's Resume Discovery operation does not find a matching candidate for this reason, You MUST make that visible rather than silent: when `codebase_path` was left at its default on an invocation that mints a new session, record on the checklist that no matching candidate was found and that `codebase_path` was not passed explicitly, so the engineer can tell a genuinely new project apart from a resume that missed its match because of this.
- **skip_phases** (optional, default: none): Comma-separated phases to skip — `elicitation`, `codebase-analysis`, `requirements`, `design`, `design-review`, `feature-splitting`, `specs`, `implementation`, `code-review`, `testing`, `documentation`.
- **output_dir** (optional, default: `.konductor/`): Directory for the markdown artifacts this SOP produces, one subdirectory per phase, plus the session state file under `output_dir/sessions/` (see Progress Tracking and Artifact Layout). Implementation code is not written here — it follows the project's own structure. You MUST resolve `output_dir` to an absolute path at intake, before any worktree exists: Steps 7 through 9 can run inside per-feature worktrees with their own working directories, where a relative path would name a different directory in each one and scatter the artifacts. You MUST verify the resolved absolute path exists (or can be created) and is writable before proceeding past intake — if it is neither, stop and ask the engineer for a usable directory rather than discovering the failure mid-run. If `reply_channel_available` is `false` (an unattended run with no reply channel), You MUST mark this step BLOCKED on the checklist with the unusable path named and stop — the same handling as Step 0's `project_description` gate. **An unattended run (no reply channel) MUST be given `output_dir` explicitly rather than left at its default.** This is an operational hygiene requirement, not an identity guarantee: passing `output_dir` explicitly only keeps an unattended run from sharing the crowded default directory by accident — it does not, by itself, prove a matching candidate belongs to this project. Two different callers (a CI template that hardcodes the same `output_dir` for every project it builds, for example) can pass the identical explicit path for genuinely unrelated work. What actually distinguishes them, when both are real git repositories with independent histories, is `project_signature`'s path fingerprint (see Progress Tracking and the `sop-state-management` skill) — not the mere fact that a path was spelled out. That fingerprint only discriminates callers when it reflects a real git lineage: two greenfield or non-git callers instead both produce the skill's `no-git-identity` sentinel and are indistinguishable by fingerprint alone (see the greenfield known limitation below) — there, safety comes from the skill's own sentinel-fingerprint check refusing to adopt a match on that sentinel, not from the fingerprint being unique. If `output_dir` is at its default and `reply_channel_available` is `false` (no reply channel exists), You MUST mark this BLOCKED on the checklist with the reason — an unattended run cannot safely share the default directory with another project — and stop at intake, before Step 0. An attended run MAY keep using the default. Resumption in an attended run is a pause point (see the `sop-state-management` skill's Resume Discovery operation, invoked per Progress Tracking below): You MUST report the candidate and wait for the engineer's explicit confirmation before adopting it — this is what actually lets a human decline a wrong resumption, rather than an assumption that presence alone accomplishes it.
- **elicitation_depth** (optional, default: `standard`): Step 0 question budget — `quick` (5), `standard` (10), `deep` (15).
- **max_fix_cycles** (optional, default: `2`): How many times a step retries its own fixes before escalating to the engineer. The budget is per feature for the whole run, not per step — Steps 7, 8, and 9 draw from one shared count so a feature with sticky findings cannot churn past what the engineer allowed. The count lives in the session state file (`output_dir/sessions/k-full-sdlc-<timestamp>-<suffix>.yml`, managed via the `sop-state-management` skill) as each feature's `fix_cycles_used`, starting at 0 when Step 5 creates the feature entry; Steps 7, 8, and 9 read and increment it — see Progress Tracking. Step 10 draws on this same limit too, but through its own run-level `doc_fix_cycles_used` counter rather than the per-feature one — its documentation validation is project-wide, not per-feature, so there is no feature slug to attach it to; see Progress Tracking and Step 10.
- **deployed_url** (optional): URL of the running application. Required for the functional and UI test passes in Step 9; without it those passes are skipped.
- **credentials_file** (optional): Path to a `.properties` file with `test_url`, `user_name`, `password` keys, for a `deployed_url` that requires authentication. Forwarded to `k-e2e-test-generation` and `k-light-ui-testing` in Step 9 as their own `credentials_file` parameter — both declare it. Without it, both SOPs treat `deployed_url` as a public, unauthenticated app.
- **feature_isolation** (optional, default: `branch`): How per-feature work is separated — `branch` for one branch per feature in a single working directory, or `worktree` for a separate git worktree per feature. Only `worktree` supports implementing features in parallel.
- **reply_channel_available** (optional, default: `true`): Whether an engineer is reachable to answer questions during this run. This is the checkable fact behind every "unattended run with no reply channel" branch in this SOP — set it explicitly to `false` for a batch, CI, or other fully automated invocation with no one to ask; leave it at the default `true` for a normal interactive session.

**Constraints for parameter acquisition:**

- You MUST have `project_description` before proceeding — if not provided, ask once and wait. If no reply arrives and `reply_channel_available` is `false` (an unattended run with no reply channel), You MUST mark this step BLOCKED on the checklist and stop rather than waiting indefinitely — a hang here produces zero artifacts, which is worse than an explicit early stop.
- If `reply_channel_available` is `false` (an unattended run with no reply channel), `output_dir` MUST be passed explicitly, not left at its default — see that parameter's own entry above for why, and mark this BLOCKED at intake, before Step 0, if it is not.
- You MUST NOT ask for the other parameters — use defaults and proceed.
- Before starting a phase whose inputs come from a skipped phase, You MUST check for pre-existing artifacts and ask the engineer to supply them if missing. Find the phase's artifacts in the Artifact Layout below — the phase name is not always the directory name. `feature-splitting` writes to `feature-split/`, `design-review` writes into `design/`, `elicitation` writes no file at all, and the per-feature phases `code-review` and `testing` write under `{feature-name}/`, while `specs` writes under `specs/{feature-name}/`. For `specs`, also check `.konductor/specs/{feature-name}/` and `.kiro/specs/{feature-name}/`: the former is where Step 6 below writes the specs when this SOP produced them (it overrides `kiro-spec-workflow`'s `spec_dir` to `output_dir/specs/{feature-name}/` so everything stays under one `output_dir`), the latter is `kiro-spec-workflow`'s own default when an engineer ran it directly rather than through this SOP — check both, since either path is possible depending on how the specs were actually produced. If `reply_channel_available` is `false` (an unattended run with no reply channel), You MUST treat a missing required artifact from a skipped phase the same as every other blocking gate in this SOP: mark the dependent phase BLOCKED on the checklist with the missing artifact named, and stop, rather than guessing its content.

Every default in this SOP is an opinion, not a constraint. If the engineer asks for something different — a different layout, extra README sections, one pull request instead of per-feature — follow their instruction and note the deviation in Step 11.

**Steering messages are scoped to what they name.** A steering message narrows only the aspect it addresses and MUST NOT be read as waiving any other approval gate or MUST-level instruction: Step 4's CRITICAL-findings gate, Step 5's feature-split approval, Step 6's per-feature spec approval, Step 7's no-worktree-removal-with-uncommitted-work prohibition, Step 8's consolidated-verdict gate and no-merge prohibition, and Step 9's CRITICAL-gap acceptance gate and two-question gate.

## Execution Rules

You coordinate; you do not implement. Every phase runs in a subagent.

Route by the task, not by the step number. For a step's own task category, this table names the agent to spawn:

| Task                                                        | Agent                 |
| ----------------------------------------------------------- | --------------------- |
| Existing codebase analysis                                  | `k-developer`         |
| User stories, requirements, acceptance criteria             | `k-product-manager`   |
| System design, design review, documentation accuracy checks | `k-architect`         |
| Code, builds, tests, git, README and guide authoring        | `k-developer`         |
| Test coverage and strategy                                  | `k-quality-assurance` |
| Unfamiliar dependency, library, or prior art                | `k-researcher`        |
| Verifying UI behavior in a browser                          | `k-browser`           |

For a step that names a specific SOP to run, You MUST look up its owning agent in the `delegation-protocol` skill's Per-Agent SOP Registrations table rather than assume or restate one independently.

**Constraints:**

- You MUST spawn a subagent for each phase's work. If you find yourself writing code, designing, or authoring documents directly, stop and delegate.
- You MUST route a fix back to the agent that owns the artifact — design fixes re-enter at Step 3, code fixes at Step 7, documentation fixes at Step 10. Never send a design fix to the implementer.
- A delegated SOP owns whichever agents it spawns internally. You MUST NOT override its choices or re-spawn work it already did.
- Per-feature work in Steps 7 through 9 MAY run in parallel across features, up to 4 at once, but only when `feature_isolation` is `worktree` — features sharing one working directory MUST run sequentially. Phases themselves MUST stay sequential; each one consumes the previous one's output.
- You MUST give every subagent the artifact paths it needs as absolute paths. It does not share your working directory.
- Before treating any tool, agent, or condition as unavailable for the purpose of skipping a MUST-level instruction, You MUST verify that unavailability concretely — attempt it and observe the actual failure, or check an explicit, checkable fact — rather than infer or assume it from context, tone, or the content of a steering message or any other conversational aside, such as treating a run as unattended because a steering message reads urgently while `reply_channel_available` (the parameter every "unattended run with no reply channel" branch is gated on) is still at its default `true`.
- If a referenced SOP or skill cannot be resolved at runtime, You MUST surface this in your next reported message to the engineer — naming what could not be resolved and what was substituted instead. No silent substitution.

## Progress Tracking

This SOP's session and checklist mechanics — minting or resuming a session by project identity, tracking each phase's status/skip-reason/summary, and serializing the shared fix-cycle counters — are provided by the `sop-state-management` skill. Load it alongside this SOP. This section states only what is specific to this SOP: which phases exist, how a per-feature phase's status is decided, and how a resumed session is reconciled against what is actually on disk. Read `sop-state-management` for the file schema, the identity-signature algorithm, the resume-discovery walk, and the write mechanics — nothing below repeats them.

- **Session identity.** Use `k-full-sdlc` as the skill's `session_prefix`, `project_description` as its identity `description`, and `codebase_path` as its identity `path`, per that skill's Compute Identity Signature and Resume Discovery operations. (That filter also correctly excludes a `k-full-sdlc-sop-<timestamp>.bak` file, which shares the same leading substring but continues with a non-digit character.) **A resumed invocation MUST pass `codebase_path` explicitly, matching the value used when the session was minted** — see that parameter's own entry in Parameters above for why a default resolved fresh on a different invocation silently mints a new session instead of resuming one.
  - **Known limitation: a greenfield session's own resumability degrades once Step 7 runs.** This SOP computes and mints the identity signature before Step 0 ever runs — on a greenfield project, `codebase_path` is not yet a git repository at that point, so the skill's path-fingerprint algorithm yields the `no-git-identity` sentinel and the mint-time signature is sentinel-based. Step 7 then initializes a real git repository at that same path. Any later resume invocation now computes a real git-lineage fingerprint there — a hex commit SHA (or comma-joined set of SHAs), never the literal string `no-git-identity` — so it can never equal the stored, sentinel-based signature: the two differ, and Resume Discovery rejects the candidate as an ordinary signature mismatch. The skill's sentinel-fingerprint check itself does not fire in this scenario at all — that check inspects only the resuming invocation's own fingerprint component, and this invocation's is real-lineage, not sentinel (see that skill's Resume Discovery operation). A greenfield run therefore silently mints a brand-new session on every resume attempted after Step 7 has run, losing the prior session's phase, feature, and fix-cycle state. This is a known limitation of the skill's identity mechanism, not something this SOP works around — treat any resume of a greenfield project past Step 7 as a fresh start, and warn the engineer of this if a greenfield resume is attempted.
- **Phase list.** This SOP's phases, in order, are: `elicitation` (Intake Elicitation), `codebase-analysis` (Codebase Analysis), `requirements` (Requirements), `design` (Design), `design-review` (Principal Engineer Design Review), `feature-splitting` (Feature Splitting), `specs` (Specs (Per Feature)), `implementation` (Implementation), `code-review` (Code Review and Pull Request), `testing` (Testing), `documentation` (Documentation), and `final-summary` (Final Summary) — the same ids as Steps 0 through 11 and the `skip_phases` parameter, plus `final-summary`, which has no `skip_phases` token of its own because Step 11 cannot be skipped. Resolve this before Step 0 ever runs, via the skill's Resume Discovery operation (per the Session identity bullet above): if it resumes an existing session, adopt its returned `phases` map as-is rather than re-minting it; only if it finds no matching candidate do you then mint the session with this full phase list and this run's `skip_phases` as the skip set via the skill's Mint Session operation, marking each `skip_phases` phase `SKIPPED` up front the same way the checklist below does.
- **The checklist and the skill's `phases` map coexist by design — one does not replace the other.** `sdlc-checklist.md` remains the human-readable record you display at every engineer pause: phase status, feature status, artifact paths, and free-text detail a fixed schema cannot hold — a re-derived status, an unverified completion, a named blocking reason. The skill's `phases.<phase-id>` entries are the structured counterpart: what a resumed session re-parses to know where it left off without re-reading markdown prose, the same reasoning that already keeps `fix_cycles_used` and `e2e_project_dir` out of the checklist. You MUST update both on every phase-status change, through the skill's Write Safety order (state file first, checklist second) — never one without the other, and never as a single batched or parallel dispatch: per the skill's own sequential-dispatch requirement, you MUST NOT hand off the checklist write until the delegated state-file write has returned confirmed success. You MUST display the checklist at every point where you pause for engineer input, including the attended-mode Resume Discovery pause; see that operation for the one case (before the checklist is first created) where the engineer is asked directly instead.
- **Per-feature phase completeness (Steps 6 through 9).** The skill's Read/Write a Phase Entry operation has no opinion on when a per-feature phase is done — that judgment belongs here. For `specs`, `implementation`, `code-review`, and `testing`, You MUST track per-feature state on the checklist, not just per-phase, and call the skill's phase-write operation for the phase itself only once you have decided: `IN_PROGRESS` from the first feature entering the phase, `COMPLETED` with a summary once every feature has cleared it, and `BLOCKED` only if the phase itself is stopped for every remaining feature. A single feature left BLOCKED while others continue leaves the phase-level entry `IN_PROGRESS` — the checklist's per-feature detail is where that one feature's block is visible.
- **Fix-cycle counters.** Steps 7, 8, and 9 draw from one counter per feature, named `fix_cycles_used`, via the skill's Register a Feature and Read/Increment a Counter operations. Each feature MUST be registered as soon as it is known: Step 5 does this immediately after `task-decomposition` returns its output, or, when `feature-splitting` is in `skip_phases`, whichever step first reads the externally-supplied `feature-split.md` does it in Step 5's place, per the pre-existing-artifact check in Parameters above. Step 10 draws from its own run-level counter, `doc_fix_cycles_used`, since its documentation validation is project-wide, not per-feature — there is no feature slug to attach it to. Both draw on the same `max_fix_cycles` limit but are otherwise independent. Because Steps 7, 8, and 9 MAY run up to 4 features in parallel under `worktree` isolation, You MUST follow the skill's concurrency rule for every write against the session file, not `fix_cycles_used` alone: hold the skill's mutual-exclusion primitive (see Read/Increment a Counter's Concurrency scope) across each feature's full read-increment-write cycle, so no two features' writes — counter, phase, or opaque-data — ever overlap on the shared session file. Two features' cycles MUST NOT interleave between a read and its matching write. A feature blocked on another feature's held lock MUST follow the skill's stale-lock recovery rule rather than retry without limit: past the fixed 30-second threshold the lock is treated as abandoned — the holding feature's process crashed mid-cycle rather than merely running long — and stolen, applying the skill's TOCTOU-safe mtime re-check immediately before removal.
- **Other run- and feature-level fields.** Store `feature_isolation` (this run's parameter, written once at minting and never overwritten by a later invocation's parameter value) and `e2e_project_dir` (run-level under `branch` isolation, per-feature under `worktree` isolation — read `feature_isolation` first to know which slot is authoritative) via the skill's Read/Write Opaque Data operation.
  - **Reconciliation on resume (feature_isolation).** Whether resumed automatically or by an explicitly named file, if this run's `feature_isolation` parameter differs from the resumed session's stored value, You MUST NOT adopt either silently. This is a hard stop for the whole run: mark the run BLOCKED on the checklist, name both values and the resumed session's file path, and stop pending the engineer's explicit choice — either re-invoke with `feature_isolation` matching the stored value to continue this session under its original strategy, or start a fresh session (a new or distinct `output_dir`) to use a different strategy for what is, at that point, new work rather than a continuation. A brand-new session has no stored value to conflict with — it simply records this run's `feature_isolation` parameter as its own, via the skill's Read/Write Opaque Data operation immediately after minting (Mint Session itself has no slot for this field; it initializes `run.data` empty). This check happens once, here, at resume — every branch or worktree operation in Step 7, for every feature, at any point in this or a later resume of the same session, MUST use the value the session actually stored, never a value re-read from a later invocation's own parameter.
- **Ownership.** You alone invoke the skill's operations and own the checklist. Spawned agents MUST report their status back to you rather than writing either directly, so parallel feature work cannot corrupt them. You MUST carry each phase's artifact paths on the checklist as they are produced — Step 11 reads from it. You MUST delegate the actual file writes — both the skill-owned session file and `sdlc-checklist.md` — to a subagent (`k-developer`), passing the exact content to write, the same as every other artifact this SOP produces: you alone decide what and when to write; the subagent performs the write. This keeps checklist and state ownership with you without requiring you to hold a standing file-write tool grant.
- **Pre-step reconciliation gate (every step, not only at resume).** Before delegating any step's own work — Steps 0 through 11, every pass through this SOP — You MUST read this session's `phases` map via the skill's Read/Write a Phase Entry operation and compare it against `sdlc-checklist.md`'s current phase status. For Steps 6 through 9, You MUST additionally confirm every feature slug on the checklist still has a corresponding entry in this session's `features` map. The `phases` map itself carries no per-feature slot — a feature's completion status is never duplicated into session state; it lives on the checklist alone, re-derived from disk when it needs correcting (see the Post-resume consistency check below) — so the only thing session state can disagree with the checklist about, for a feature, is whether that feature is registered at all, never what phase it has reached. Skip this gate on the first step of a freshly minted session, where no checklist yet exists. The fixed Write Safety order (state file first, checklist second) makes only one direction of disagreement a legitimate crash outcome; handle the two directions differently:
  - **State file ahead of the checklist** — the `phases` map already shows a phase done while the checklist still shows `PENDING` or `IN_PROGRESS`. This is what a crash between the state-file write and its paired checklist write produces. You MUST update the checklist to match the `phases` map — per-feature detail via the expected-artifact re-derivation in the Post-resume consistency check bullet below — then re-display the reconciled checklist, before proceeding with this step's delegation. Leave the state file itself untouched. This direction has no feature-level counterpart: the `features` map carries no completion status for a checklist entry to lag behind.
  - **Checklist ahead of the state file** — for a phase, the checklist shows it done while the `phases` map still shows `PENDING` or `IN_PROGRESS`. The fixed write order rules this outcome out under normal operation, and because the `phases` map already has every phase ID present at minting (see Progress Tracking's Phase list bullet below), this can only ever be a status disagreement between two existing entries, never an entry missing outright. Handle it the same way the Post-resume consistency check's re-derivation bullet handles the equivalent per-feature case: re-derive the phase's actual status from disk against its own expected artifact set (this phase's Expected Output in the Steps section below; for a per-feature phase — Steps 6 through 9 — re-derive every feature's own status first, per that same bullet, then apply Progress Tracking's per-feature completeness rule to the phase as a whole), correct the checklist to match, then proceed with this step's delegation — do not stop or wait for the engineer. For a feature (Steps 6 through 9 only), the checklist lists a slug this session's `features` map is missing outright — the actual shape the Post-resume consistency check's BLOCK-and-surface bullet handles, since a `features` entry exists only once something has explicitly registered it. Apply that handling here too: mark the feature BLOCKED with the disagreement named, and stop for that feature pending the engineer, rather than writing either file.

  This gate is separate from, and applies in addition to, the post-resume check below, which runs once, immediately after a resume; this gate runs before every step of the run, resumed or not.

- **Feature-registration gate (before Step 6).** Before Step 6 begins, for every feature slug recorded on the checklist from Step 5's `{Feature Name} → {feature-name}` pairs, You MUST confirm the session's `features` map already carries an entry for that slug. You MUST register any missing slug now, through the skill's Register a Feature operation, before Step 6's first `kiro-spec-workflow` invocation. **This gate's scope excludes a feature slug the checklist already marks BLOCKED with "session state entry missing for a feature the checklist already reports on"** — that entry stays exactly as the pre-step reconciliation gate or the post-resume consistency check left it, unregistered and BLOCKED, until the engineer supplies its `fix_cycles_used` value or explicitly accepts starting it fresh at `0`; this gate MUST NOT register it in the engineer's place. A feature left unregistered outside that exception has no `fix_cycles_used` counter for Steps 7 through 9 to read from.

- **Post-resume consistency check.** Run this only after the feature_isolation reconciliation check above has already passed without stopping the run — a feature_isolation mismatch is a hard stop for the whole run, before any feature-level state is even relevant, so it takes precedence over this per-feature comparison, not the reverse. Once past that gate, immediately after the skill's Resume Discovery operation resumes a session, and before doing any further phase work, for every feature slug, compare (a) whether it is present in the resumed `features` map versus the checklist, and (b) where present in both, whether the checklist's recorded phase status for it agrees with what actually exists on disk. Comparing only the _set_ of slugs is not enough — a feature present in both, whose recorded status disagrees with the artifacts after a crash mid-transition (the checklist still shows the previous phase, or already shows the next one, while the artifacts on disk tell a different story), would otherwise go undetected.
  - **Re-deriving a phase status from disk requires the phase's full expected-artifact set, not any single artifact.** Each phase's expected set is fixed: `specs/` is only complete once `requirements.md`, `design.md`, AND `tasks.md` all exist (`kiro-spec-workflow` writes these three in sequence, so a crash after the first one or two leaves `specs/` non-empty but incomplete); `code-review/` is only complete once both `report.md` AND `status.md` exist; `testing/` is only complete once `k-test-coverage-review`'s own `test-gap-analysis.md`, `e2e-test-strategy.md`, AND `test-coverage-review-report.md` all exist (this is the same principle Step 9 already applies when distinguishing a real testing pass from a Kiro-stub `tasks.md`-only directory). A subtree that has artifacts present but is missing any one file from its phase's expected set has NOT completed that phase — the correct re-derived status is the deepest phase whose full expected set is present, one phase earlier, never the partially-populated one.
  - **Implementation (Step 7) cannot be re-derived from `output_dir` by this expected-artifact-set method at all.** Unlike `specs/`, `code-review/`, and `testing/`, Implementation writes to the project tree, not under `output_dir` — there is no `output_dir/{feature-name}/implementation/` subtree for this mechanism to inspect, by design (see Artifact Layout: "Implementation code, tests, and build configuration go where the project puts them"). Its only observable signal from inside `output_dir` is the checkbox state of `output_dir/specs/{feature-name}/tasks.md` — already inspectable, since `specs/` is under `output_dir` — plus whatever the project's own git state shows outside it. Apply this rule where `specs/` is re-derived as complete but `code-review/` is not (code review presupposes implementation, so a complete `code-review/` subtree already implies Implementation finished; this rule only matters in the gap between the two): if any task in `tasks.md` is unchecked, Implementation is definitely not complete for that feature — its re-derived status stays at the deepest phase actually complete, i.e. specs COMPLETED, implementation not yet done. If every task in `tasks.md` is checked, that is necessary but not sufficient evidence — a crash could land after the last checkbox was checked off but before Step 7's own build-and-test-after-each-feature requirement confirmed the build actually passed, or the code could have been reverted since. You MUST NOT mark Implementation COMPLETED on checkbox state alone — doing so risks silently reporting an incomplete or broken Implementation as done. Instead, record that feature's Implementation as `COMPLETED (unverified — tasks.md fully checked, pending confirmation)` and mark the feature BLOCKED on the checklist pending either the engineer's explicit confirmation or a fresh re-run of the build and test commands recorded on the checklist in Step 7 passing clean; only one of those two — never the checkbox state by itself — may promote it to a bare `COMPLETED`.
  - A feature slug present in the resumed `features` map but missing from the checklist, or present in both but with a checklist-recorded status that disagrees with what the expected-artifact re-derivation above says the deepest completed phase actually is, means the checklist write either did not happen or is stale relative to what is really on disk (a crash between finishing one phase's writes and the paired checklist write, consistent with the skill's fixed write order; or a crash mid-transition into the next phase after the checklist had already recorded the previous one). You MUST re-derive that feature's status per the expected-artifact rule above, add or correct it on the checklist, and mark it distinguishably from a normally-reported status — e.g. `COMPLETED (re-derived)` rather than a bare `COMPLETED` — so the engineer can tell a status this SOP itself observed from one it reconstructed after a crash. This corrected value is per-feature detail; it lives on the checklist only — the skill's `phases.<phase-id>` entry has no per-feature slot to write it into. Separately, re-apply Progress Tracking's per-feature completeness rule to the phase as a whole now that this feature's status is corrected: if every feature has, in fact, cleared the phase (this correction included), call the skill's phase-write operation to set that phase's aggregate entry to `COMPLETED` with a summary; otherwise leave the phase-level entry as it already stands. Then write the corrected checklist back, before proceeding.
  - A feature slug present on the checklist but missing from the resumed `features` map means the checklist is ahead of the state file, which the skill's fixed write order says should not happen. You MUST NOT invent a `fix_cycles_used` value for it — reconstructing one from nothing risks silently resetting or fabricating the fix-cycle budget, exactly the risk this mechanism exists to prevent. Instead mark that feature BLOCKED on the checklist with "session state entry missing for a feature the checklist already reports on" and stop for that feature, surfacing it to the engineer, rather than guessing. **To un-block this case:** the engineer either supplies the feature's correct `fix_cycles_used` value (from their own record of how many fix cycles it actually consumed, or `0` if none) for you to register via the skill before resuming work on it, or accepts starting that feature's budget fresh at `0` — either way, the un-block is an explicit engineer decision recorded on the checklist next to the BLOCKED entry it resolves, never a value this SOP guesses on its own.
  - The skill's Resume Discovery operation already skips any malformed or sentinel-fingerprint-collision candidate it encounters along the way and reports which paths it skipped — record those paths on the checklist so the engineer can inspect them later. This check assumes the file it is comparing against already parsed successfully; a parse failure is the skill's concern, not this check's.

## Artifact Layout

```
.konductor/ default output_dir
├── codebase-analysis/analysis.md
├── requirements/                    business-context.md, requirements-summary.md, user-stories-raw.md, user-stories-extract.md
├── design/                          system-design.md, principal-engineer-review.md
├── feature-split/feature-split.md
├── specs/{feature-name}/            requirements.md, design.md, tasks.md — one subtree per feature from Step 6
├── {feature-name}/                  one subtree per feature from Steps 8 and 9
│   ├── code-review/                 report.md, status.md
│   └── testing/                     coverage and test-strategy reports, ui-prompts/
├── sdlc-checklist.md
├── sdlc-summary.md
└── sessions/
    └── k-full-sdlc-<timestamp>-<suffix>.yml   one file per session — see Progress Tracking and the `sop-state-management` skill
```

Steps 1 through 5 are project-wide and write directly under `output_dir`. Step 6 is per-feature and writes under `output_dir/specs/{feature-name}/`, matching `kiro-spec-workflow`'s own convention of nesting the feature name under `specs/` rather than the other way around. Steps 8 and 9 are per-feature and write under `output_dir/{feature-name}/`, so a feature's code-review and testing artifacts sit together in one subtree — separate from that same feature's specs — which is also what keeps parallel features' code-review and testing artifacts from overwriting each other, since the delegated SOPs write fixed filenames within that subtree. Step 7 is per-feature too, but its only touch under `output_dir` is checking off tasks in the `specs/{feature-name}/tasks.md` Step 6 already created — implementation code itself goes into the project tree, never under `output_dir/{feature-name}/`. `output_dir` holds only SDLC process records — specs, sessions, requirements, design docs, the checklist. Step 10's project deliverables (`README.md`, `developer-guide.md`) ship with the code, so they are never written under `output_dir` at all — they go directly to the project root (`codebase_path` on a brownfield project, the source directory recorded on the checklist in Step 7 on a greenfield project), alongside every other exception that escapes `output_dir` by design: Step 3's `docs/design/` reports (project-wide, named from a slug of the design topic rather than a fixed name), Step 9's `k-e2e-test-generation` pass in `add-to-existing` mode, which writes generated test specs into the project's own existing test directory rather than under `output_dir/{feature-name}/testing/`, and Step 10's repository-root `AGENTS.md` (produced only if the repo lacks one). `sdlc-summary.md` is otherwise the only project-wide artifact Step 11 adds under `output_dir`.

**Known limitation: `output_dir` is fixed, not session-scoped.** Only `sessions/` is per-session — each run's state file keeps its own timestamped name. Everything else under `output_dir` uses fixed filenames, so a second run against the same `output_dir` overwrites the first run's artifacts: `requirements/`, `design/`, `feature-split/`, every `specs/{feature-name}/` subtree, every `{feature-name}/` subtree, `sdlc-summary.md`, and `sdlc-checklist.md` all get replaced. This is accepted, not a defect — an engineer who wants to keep a completed run's artifacts must copy them out before starting the next run, or pass a distinct `output_dir`. `README.md` and `developer-guide.md` are unaffected by this — they live at the project root (`codebase_path` on a brownfield project, the Step 7 source directory on a greenfield project), not under `output_dir`, so a second run against the same `output_dir` overwrites them only if it also targets the same project root. Nothing in either mode pauses specifically to flag an impending overwrite before it happens — an attended engineer relying on the shared default `output_dir` is trusting that no other run has used it, not being warned in the moment this run replaces its content. The explicit, non-default `output_dir` required of an unattended run (see that parameter's own entry above) exists because an unattended run additionally has no engineer to ask at all, not because an attended run has some other real-time protection against the same overwrite.

`sdlc-summary.md` is the run's only rollup: Step 11 reads the per-feature status files and reports phase statuses, every artifact path, and everything left open.

`output_dir` holds only the markdown this SOP produces. Implementation code, tests, and build configuration go where the project puts them — Step 7 writes into the project tree and tracks its progress in `specs/{feature-name}/tasks.md`, so it adds nothing here.

Create a directory only when a step writes into it — a skipped phase leaves no empty directory behind.

One set of artifacts lands outside `output_dir`: `k-design-doc-creation` writes its validation and trade-off reports into `docs/design/` by default, using names derived from the topic it was given. That SOP now accepts an optional `validation_output_dir` parameter to redirect them, but this SOP does not pass it — the Step 3 subagent instead reports the two paths it actually wrote onto the checklist, and Step 11 lists them from there.

### 5. Feature Splitting

Spawn `k-developer` to split the work into independently buildable features.

**Constraints:**

- You MUST skip this step if `feature-splitting` is in `skip_phases`.
- You MUST instruct it to use `task-decomposition` with `output_dir/requirements/user-stories-raw.md` and `output_dir/design/system-design.md` as input — the raw file, not `user-stories-extract.md`. The extract keeps only 3-5 architecturally significant stories per epic for the design interview; splitting features from it would drop every story it didn't select, and those stories would never appear in any feature's scope.
- Each feature MUST be buildable independently, with minimal overlap between features.
- You MUST derive a kebab-case slug for every feature immediately after `task-decomposition` returns its output — lowercase, spaces and `&`/`/` replaced with `-`, stripped of any character outside `[a-z0-9-]`. Two feature names differing only in case, punctuation, or whitespace can derive the same slug, which would silently merge their `output_dir/{feature-name}/` subtrees (and, under `worktree` isolation, their branch and worktree names too), so You MUST assign final slugs with this algorithm, not by rechecking each candidate against a single fixed set computed once up front:
  1. Maintain one running set, `assigned-slugs`, empty at the start.
  2. Process features one at a time, in the order `task-decomposition` returned them. This order is fixed for the whole pass — never re-sort or re-batch by collision.
  3. For each feature: if its derived slug is not already in `assigned-slugs`, that derived slug is its final slug. If its derived slug IS already in `assigned-slugs` — because an earlier feature in this same pass claimed it, or because another feature's own free-text name already normalizes to it (e.g. a feature literally named "X 2" alongside a feature named "X") — try `{slug}-2`, then `{slug}-3`, `{slug}-4`, and so on, checking each candidate against `assigned-slugs`, until reaching a candidate not in the set. That candidate is this feature's final slug.
  4. Immediately add the feature's final slug to `assigned-slugs` before moving to the next feature. This is what makes the check accumulate: a later feature's candidate is checked against every slug already claimed in this pass, not against the original pre-disambiguation set, so two features colliding on the same base slug can never both be assigned the same disambiguated candidate.
  5. Record on the checklist every feature whose final slug differs from its bare derived slug.

  Only once every feature has been processed — and every final slug is therefore already unique by construction — record the final `{Feature Name} → {feature-name}` pairs on the checklist. Every subsequent step MUST use this recorded slug, never the free-text feature name, as `{feature-name}` in any path or branch name.
