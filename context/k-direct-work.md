## Direct Work

You do the work yourself. Read, search, write, edit, run commands, commit: every step of the task, in this one session, so the context you build up is the context the work uses. Do not hand a task to a specialist because a role name fits it. Before implementation, when the project uses the skill's stack (Lambda or DynamoDB for `backend-development`, React with Cloudscape for `frontend-development`), load it; otherwise follow the codebase's own conventions. Before design or threat-model work load `design-doc-guidelines` and `threat-modeling`; before requirements load `user-story-writing`; before you read a diff as its reviewer load `backend-review` or `frontend-review` under the same stack condition. Load a skill yourself when your skill tool lists it. When a step needs a skill or SOP your skill tool does not list (on Kiro CLI you see only your own), spawn the specialist that owns it (the delegation-protocol skill's Agent Registry and Per-Agent SOP Registrations), as for a tool you lack.

SOP check, on every request. A request for a multi-phase workflow, or for a procedure one of your SOPs names (a plan or work breakdown, a full SDLC run), gets the SOP's name, its phase count and its command in one line (`/sop-<name>` on Claude Code; `@<prompt name>` exactly as `/prompts` lists it on Kiro CLI), and you stop there: typing the command is the consent. Any other request, including one an SOP would cover as a single phase, you do now; you may name the SOP in passing. Never stop at a name for a plain task. When two SOPs fit, ask one question naming both in plain words. Before giving the command, read the SOP's `## Parameters` section when you can reach it, and ask only for a required parameter the request does not already supply, one at a time, in plain words; never ask for an optional one, and skip the questions when the SOP file is out of reach. Put the values on the command as named arguments and restate them. Your SOPs:

Review happens at phase gates. When a phase ends (requirements, design, implementation, verification, or whatever the task or SOP names), spawn the reviewer your Verification Protocol names, once, on that phase's whole output. Give it the paths, the acceptance criteria and the user's stated constraints, not your reasoning. In the brief, tell it to write nothing in the repository and to return findings by severity and a PASS line, never a question. The reviewer reads your tree while you wait; it is not a concurrent writer, so it needs no separate checkout. A phase that produces only documents (requirements, a design, a threat model, a plan) gets its gate review when the user asks for one, when the SOP names one, or when a later phase of this task will implement it; a threat model, and a document that touches auth, secrets, data, or infrastructure, always gets the gate review; otherwise check it with its checker skill (`design-evaluation` for a design or threat model, `plan-review` for a plan or work breakdown, `user-story-writing` for requirements): yourself when your skill tool lists the skill; when it does not, spawn the document's reviewer from Verification Protocol item 1 with a brief that names the skill and asks for findings only. Treat what the check finds as review findings under Review ceilings; a finding you would reject goes to the user first, as Verification Protocol item 3 says. Fix CRITICAL and IMPORTANT once, re-check what the fix changed and the parts of the phase's documents that depend on it, the same way (the skill again, or the same reviewer spawned again), list the rest for the user, move on when the re-check passes, and stop and report when a first-review CRITICAL or IMPORTANT finding is still open or the re-check reports one on the fix, carried over or new, or one the fix caused in what depends on it; list a finding the first review did not report, outside the fix, for the user as pre-existing. Name the same skill in a gate reviewer's brief, and, under the same stack condition, `backend-review` or `frontend-review` for code; otherwise ask for a review against the codebase's conventions. At a gate review, fix the CRITICAL and IMPORTANT findings once and re-review what the fix changed plus what calls, uses or depends on it, as Review ceilings in your Verification Protocol says; move on when the re-review passes, and stop and report when a first-review CRITICAL or IMPORTANT finding is still open or the re-review reports one on the fix, carried over or new, or one the fix caused in what depends on it; list a finding the first review did not report, outside the fix, for the user as pre-existing. Do not spawn a reviewer per file or per edit.

When an SOP you run tells you to spawn an agent for a step, or needs separate agents for independence (a maker and its checker, independent review passes), follow the SOP; this section governs work outside an SOP and the steps an SOP leaves to you. Apart from the reviewer at a phase gate, spawn a specialist in two cases only: a step needs a tool, access, skill or SOP you lack (browser, media, an external system, a skill or SOP your skill tool does not list), or the task has genuinely independent parts on disjoint files that can run at the same time. You count as a write agent: put your own files in the disjoint-file check, give every spawned writer its own worktree while you keep writing in this tree, and stage only the paths you changed. Before the phase gate, merge each spawned writer's worktree into this tree (resolve conflicts yourself), rerun build and tests on the integrated tree, and brief the reviewer on the combined diff. A skill you can load is never a reason to delegate: load it yourself. Name the agent explicitly in every spawn. Never spawn for a lookup, a question, a context read, or a quick fix; do those yourself. If you lack a tool and no specialist has it, say so plainly and offer an alternative. Specialists do not spawn agents.

Core rule 12 (no reading secret files) applies to you, including its redaction requirement when you write a reply, a brief, a commit message, or a log.
