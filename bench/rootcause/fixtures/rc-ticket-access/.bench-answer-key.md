# rc-ticket-access answer key

Judge-only. Runners must not copy this file into the agent working directory.

Input: `docs/access-patterns.md`. Output expected: `docs/data-model.md`, a DynamoDB design. No code and no change to the input. There is no test command.

## Seeded design points

| ID | Pattern | What a good design does |
|----|---------|-------------------------|
| DY1 | AP1, AP4, 10,000 comments | Keeps comments as separate items in the ticket's item collection (same partition key, a sort key that orders comments by time) and does not store comments as a list attribute on the ticket, because an item is capped at 400 KB (10,000 comments of 2 KB is about 20 MB). One Query with a limit of 50 and `ScanIndexForward=false` serves AP4. AP1 is a GetItem with `ConsistentRead`. |
| DY2 | AP2 | A global secondary index on customerId with createdAt as the sort key, read newest first with pagination (`LastEvaluatedKey`). Notes that a GSI read is eventually consistent, which AP2 allows. |
| DY3 | AP3 | A sparse global secondary index for open tickets: partition key assignedAgent, sort key priority combined with createdAt. Only tickets that are open and assigned carry the index attributes; they are removed when the ticket closes. |
| DY4 | AP5 | Lookup by externalRef through a global secondary index, or through a separate lookup item keyed by the reference. Uniqueness is enforced with a conditional write (attribute_not_exists) in a transaction, because a GSI cannot enforce uniqueness. |
| DY5 | AP6 | Does not serve the dashboard with a Scan or with a status index (four values, so each value is a hot partition holding 100 million items). Maintains counters from the table's change stream (or an export to an analytics store), refreshed every minute. |
| DY6 | AP7 | `TransactWriteItems` with an update of the ticket (condition: status is not closed) and a put of the audit entry. States that a transaction costs double the capacity. |
| DY7 | Capacity | Picks a capacity mode (on-demand, or provisioned with auto scaling) with a reason tied to the stated rates (spiky mix of 2,000 reads/s, 600 writes/s for comments) and estimates or reasons about per-partition limits (1,000 write units and 3,000 read units per partition per second); names the 200,000-ticket customer as the key to watch. |
| DY8 | Trade-offs and lifecycle | Names at least one rejected alternative with a reason (a status GSI, one table per entity, comments inside the ticket item, relational database) and addresses the 7-year retention with 90-day hot data (TTL on comments or tiering/archiving to cheaper storage, an Infrequent Access table class). |

## Quality checks

- Every access pattern AP1 to AP7 names the table or index and the key condition.
- The key schema is concrete (attribute names and a key format such as `TICKET#<id>`), not just "a partition key".
- Item shapes are given for ticket, comment and audit entry.

## False claims to watch

- Says a GSI can enforce uniqueness, or that a GSI read can be strongly consistent.
- Says a Query can sort by an attribute that is not a sort key of the table or index.
- Says a transaction spans more than the allowed item count or that a Scan is acceptable for the dashboard.
- Designs a relational schema, joins or secondary indexes DynamoDB does not have (LSIs added after table creation).
