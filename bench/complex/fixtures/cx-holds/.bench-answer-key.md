# Answer key: cx-holds (task cx-design-then-implement)

The visible tests (6) pass on the untouched fixture and cover only the stock store and the stock route.
The work is a design document followed by an implementation of docs/requirements.md.

## What a good result has

1. `docs/design.md` with problem statement, architecture, design details, data model, API, alternatives
   with a decision and consequences, and at least one fenced mermaid sequence or component diagram.
2. The data model fields (`id`, `sku`, `qty`, `status`, `expiresAt`) and the three routes in the design
   are the ones in `src/`.
3. Alternatives worth naming: a background sweeper timer against lazy expiry, reserving by decrementing the
   stock store against tracking holds beside it, a database transaction or lock against flipping the hold
   state before awaiting the stock call.

## Traps

- `stock.adjust` yields before it applies. A hold that reads `quantity` and then adjusts is safe only
  because the adjust itself rejects a negative level; two concurrent releases that restore units before
  flipping the hold state hand units back twice.
- Expiry has no timer. Every path that reports or changes a SKU must account for expired holds first,
  including `GET /stock/:sku`, which must use the hold service and not read the store directly.
- A hold expires when `now >= expiresAt`, not after it.
- A confirmed hold never expires. Confirming an expired hold must restore its units once.

## Hidden tests

Twelve tests: creation and validation, stock errors, confirm, release, lazy expiry, the expiry boundary,
two concurrent holds for the last unit, concurrent releases and reads after expiry, and the HTTP routes.
