# plan-inventory answer key

Judge-only. Runners must not copy this file into the agent working directory.

Input: `docs/feature-request.md`. Output expected: `docs/plan.md`, a work breakdown only. No code and no change to `src/`, `test/`, `README.md` or the request. The service is in-memory (`src/db.js` stands in for a SQL driver); handlers return `{ status, body }`; `adjustStock` has a read then write with two awaits. Baseline: `node --test` reports 8 passing tests.

## Required parts

| ID | Part | Notes |
|----|------|-------|
| PT1 | Schema migration and backfill | Not in the numbered list. Comes from the platform note: a reservations table and a way to hold reserved quantity, with existing items backfilled to nothing reserved. |
| PT2 | Reservation service | Reserve and release, 15 minute expiry, available quantity as stock minus active reservations. Must be safe when 50 requests hit one item. |
| PT3 | Routes | `POST /items/:id/reserve` and `DELETE /reservations/:id`: admin token, 400, 404 and 409 handling. |
| PT4 | Read paths | `GET /items/:id` shows stock and available. The reorder report uses available quantity. |
| PT5 | Documentation | README: routes, error codes, the 15 minute rule. |

## Dependency edges the plan must show

| ID | Edge | Why |
|----|------|-----|
| DE1 | PT1 before PT2 | The service reads and writes the new schema. |
| DE2 | PT2 before PT3 | The routes call the service. |
| DE3 | PT2 before PT4 | Both read paths use the available quantity from the service. |

A dependency of tests or other tasks on PT2 is accepted and is not a required edge.

## Parallel part

| ID | Part | Why |
|----|------|-----|
| PA1 | PT5 | The request fixes the route contract, error codes and the 15 minute rule, so the README can be written while the code is built. A plan that puts it last in a serial chain does not mark it parallel. |

## Hidden trap

| ID | Trap | What a good plan does |
|----|------|-----------------------|
| TR1 | Migration order | The migration and the backfill of existing items must be applied before the version that reads the new data is deployed. Otherwise existing items show a missing reserved value and the available quantity breaks. The plan makes the migration the first task, includes the backfill, and says deploy order. |

## Non-functional requirement to test

| ID | Requirement | What a good plan does |
|----|-------------|-----------------------|
| NF1 | 50 reserve requests for one item within one second must never oversell | The plan has a task or a done check that runs a concurrent reservation test, and the service task names an atomic check (a lock, a conditional update or one transaction). |

## Gold plating (not asked for)

Customer accounts, email or push notices, a reservation history screen, per-customer limits, a queue service or cache layer, a new auth scheme, reporting dashboards. One mention in the risks as out of scope is fine; a task for it is gold plating.

## Good plan form

5 to 10 tasks, each with an id, scope, a done check that can pass or fail (a command, a test name or an observable result), and the tasks it depends on. Parallel tasks marked. A risks section with a mitigation or a spike for each risk. Tasks small enough to be one concern each. No code.
