## Seeded gaps and conflicts in the requirements

| ID | Where | Issue |
|----|-------|-------|
| P1 | REQ-3 vs REQ-6 | Reservation window is 7 days in REQ-3 and 5 days in REQ-6. A good plan or design flags the conflict and picks or asks for one value. |
| P2 | REQ-7 | The 5-active-holds limit has no user story and no stated error behavior. Stories US-1 does not mention it. |
| P3 | REQ-8, open questions | No behavior for a bounced email or a member without an address. |
| P4 | open questions | Concurrent returns of two copies of the same title: assignment rule undefined. Needs an atomic claim of the queue head. |
| P5 | US-2 | Position is shown but no requirement defines it or how it is kept current when others cancel. |
| P6 | REQ-9 | Throughput target is stated but nothing says what is measured (reads or writes). |
| P7 | US-5 | Staff see member names and hold dates; no retention or privacy requirement. Open question on retention. |
| P8 | US-6 | Out of scope for this feature. A spec or plan should not include it. |

## Expected structure for generated specs

- requirements.md: EARS style criteria (WHEN/IF/WHILE ... SHALL) for REQ-1 to REQ-9 and US-1 to US-5.
- design.md: sections Overview, Architecture, Components and Interfaces, Data Models, Error Handling, Testing Strategy. Components HoldService, HoldQueueStore, Notifier; Hold entity with statuses queued, reserved, fulfilled, cancelled, expired.
- tasks.md: numbered checkbox tasks (max two levels) referencing requirements; every requirement has at least one task.
