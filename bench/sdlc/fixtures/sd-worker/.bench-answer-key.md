# Answer key: sd-worker (task sdlc-prod-readiness)

The visible tests (3) pass on the untouched fixture and say nothing about the checklist.

## Seeded defects in `src/worker.js`

1. P1: a live key literal `sk_live_...` in the source, passed to the handler and written into the failure log line.
2. P2: no configuration: concurrency is a parameter with no check, no `WORKER_*` variable is read, nothing fails at
   start.
3. P3: free-text `console.log` lines with no level, and the failure line holds the key.
4. P4: no metrics and no health.
5. P5: `stop()` sets a flag and returns at once: it neither waits for jobs in flight nor bounds the wait.
6. P6: a handler that throws at once is caught only because of `await`; nothing counts it.

## Intended resolution

`src/config.js` reads `WORKER_API_KEY`, `WORKER_CONCURRENCY` (1 to 16, default 2) and `WORKER_DRAIN_MS` (0 to 60000,
default 5000) once, with a `ConfigError` naming the variable. The worker logs one structured entry per job, keeps
`processed`, `failed` and `inFlight`, reports `health()`, and `stop()` takes no new job and waits up to the drain
bound. `docs/RUNBOOK.md` lists alarms on metrics the code emits and the cost:
3,000,000 / 1,000 x 0.20 USD = 600 USD a month (cost driver: the billing calls).

## Traps

- Moving the key to a constant in another file instead of reading it from the environment.
- Logging the whole error object or the handler context, which holds the key.
- A `stop()` that waits forever for a stuck job, or one that drops jobs it already took.
- A take still waiting at stop that later swallows a job pushed to the queue.

## Hidden tests (12), cover

the three settings and their errors, the default and the set concurrency, the key from the environment, no key
literal in `src/`, the failure log entry, a handler that throws at once, no key in any log entry, health before,
during and after, a drained stop that leaves untaken jobs in the queue, and a stop that times out.
