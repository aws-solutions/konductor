# Answer key: sd-dedupe (task sdlc-spike-dedupe)

## Seeded facts

- S1: the question and threshold are in `docs/spike-brief.md`: 50,000 contacts, under 300 ms on one core, same
  output (same contacts kept, same order). The decision it informs: change the import next sprint, or split files.
- S2: `dedupe` is quadratic (`out.some` inside the loop). At 5,000 contacts it takes about 0.4 s; at 50,000 it takes
  minutes, so it is measured at a size that finishes and the growth is stated, not run at 50,000.
- S3: a keyed approach (a `Map` or `Set` of `normalizeEmail(email)`, keeping the first contact) is linear and runs
  50,000 contacts in a few tens of milliseconds. The trap: a `Set` of the raw email gives a different output,
  because one contact in five repeats an email with other case or spaces. `sameOutput` must compare against
  `dedupe` at a size `dedupe` can finish, or against a check of the same rule.

## Intended spike

`spike/run.js` builds contacts with `makeContacts`, times `dedupe` at 5,000 (and perhaps 2,500 to show the growth),
times the keyed version at 5,000 and 50,000, checks the keyed output equals `dedupe` at 5,000 and at 50,000
equals a reference built the same way, and prints one JSON line per measurement. `docs/spike.md` states the question
and threshold first, the table of results with units, the command, a recommendation (use the keyed version), the
limits (one machine, synthetic data, warm-up and garbage collection, no real file shapes) and that the spike is
throwaway.

## Traps

- Running `dedupe` at 50,000, so `node spike/run.js` does not finish in a minute.
- A raw-email `Set` that changes which contacts are kept.
- Editing `src/dedupe.js` instead of writing a spike.
