# refs-order-store answer key

Judge-only. Runners must not copy this file into the agent working directory.

Input: `docs/requirements.md`. Output expected: `docs/data-model.md`, a DynamoDB design. No code and no change to the input. There is no test command.

## Planted fact

The prompt asks for the team's write-sharding range and GSI maximum without giving them. Both are in `skills/dynamodb-design/references/aws-best-practices.md` (and the quality checklist in `references/design-validation-checklist.md`) of the slimmed skill, and nowhere in its `SKILL.md`:

- **Write sharding range: 200.** The suffix range is 1-200 (random) or `hash(id) % 200` (calculated). A design that states this range used the reference. A different number (10, 16, 32) is a plausible guess, not the standard.
- **GSI maximum: 5** per table (and 3 LSIs), with "more than 5 GSIs", "an access pattern used fewer than 10 times a day" and "partition key with fewer than 100 unique values" listed as red flags.

The scorer treats the 200 range as the planted fact. The GSI maximum of 5 is recorded as a second signal.

## Seeded design points

| ID | Pattern | What a good design does |
|----|---------|-------------------------|
| RD1 | AP1, AP3, AP4 | One table keyed by order: partition key the orderId, sort key that separates the order item from its events and orders events by time. AP1 is a GetItem with ConsistentRead, AP3 a Query on the order partition, AP4 a PutItem. |
| RD2 | AP2 | A GSI on customerId with createdAt as the sort key, read newest first with pagination. A GSI read is eventually consistent, which AP2 allows. |
| RD3 | AP5, AP4 | All events of a day share one time bucket, and 2,400 writes a second on one key exceeds the 1,000 write units a partition takes. The design spreads the day over shard suffixes (`DAY#<date>#<n>`) and reads every shard and merges by time. States the fan-out cost. |
| RD4 | Sharding | States the shard suffix range. The standard from the reference is 200 (planted fact). |
| RD5 | Index count | States a GSI maximum and keeps the design inside it. The standard from the reference is 5 GSIs per table (second planted signal). The nine patterns would need more than five dedicated indexes if each got one. |
| RD6 | AP9 | Does not add a GSI for a pattern used about 5 times a day. Serves it from an export, a filtered query or a scheduled scan job and says why. |
| RD7 | AP6, AP7, AP8 | AP6 uses a sparse GSI on warehouse that holds only picked orders. AP7 is served without a GSI or with a sparse one, with uniqueness enforced by a conditional write on a lookup item, since a GSI cannot enforce uniqueness. AP8 uses a carrier and day key. |
| RD8 | Capacity | Picks on-demand or provisioned with auto scaling with a reason tied to the stated rates, and notes that each event write is also written to every index that holds it. |
| RD9 | Trade-offs | Names at least one rejected alternative with a reason (one table per entity, a date-only partition key, a GSI per pattern, a scan for AP9). |

## False claims to watch

- Says a GSI can enforce uniqueness, or that a GSI read can be strongly consistent.
- Puts all events of a day on one partition key at 2,400 writes a second without sharding.
- Says a Scan is fine for AP2 to AP8.
