# Decision record: orders-api 4.18.0

**Call: roll back oa-3 and oa-4 to 4.17.3, starting 14:42 UTC.** Owner: release manager. Next update 15:15 UTC.

## Summary

4.18.0 is losing card payments that 4.17.3 does not lose. I compared the two halves of the fleet from 13:10 UTC (first
4.18.0 traffic) to 14:00 UTC. The 4.18.0 hosts soft-declined 2.49 % of authorisations; the 4.17.3 hosts soft-declined
0.54 %. The extra declines all carry one reason, a request key the gateway has already seen with another amount. I
count 84 such checkouts by the end of the window, roughly one every 40 to 60 seconds, and the count keeps rising while
half the fleet runs 4.18.0.

## Diagnosis

The payments client in 4.18.0 now gets its request key from the shared middleware (PAY-2291,
`release/RELEASE-4.18.0.md:10`). That key is built from the cart, so when a customer changes the cart and pays again,
the same key goes out with a new total. The gateway refuses it:

- `logs/payments-gateway.log:759`: `idem_key=cart-511903`, `IDEMPOTENCY_KEY_REUSED`, amount 28.63 then 20.57.
- `logs/orders-api/oa-4.log:727`: the same request on oa-4 (4.18.0) ends in `reason=idempotency_key_reused`.
- `logs/orders-api/oa-3.log:741`: the first one on oa-3, 13:10:41 UTC.

Two other signals look alarming but are shared by both versions, so they are not the release:

1. The latency jump between 13:35 and 13:55 UTC shows up on the 4.17.3 hosts too. It lines up with the maps-geo
   vendor's own incident window.
2. The 5xx rate is flat and the dashboard is green, because a soft decline comes back as HTTP 200. The dashboard is
   blind to this failure.

## Why not the other two options

Rolling forward needs a 4.18.1 that has passed CI and soaked on one host. Neither 4.18.1 build is green. Holding at
half means we keep turning customers away at the current rate with nothing coming to stop it.

## Rollback safety

0042 is the only schema change since 4.17.3. It adds columns and a table and drops nothing, so it does not block the
rollback: 4.17.3 just ignores the new parts. What we lose is the promo code feature, which matters for the 18:00 UTC
campaign email.
