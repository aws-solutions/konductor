# Incident Report: Duplicate Push Notifications

**Date:** January 15, 2024  
**Severity:** P1 (High Impact)  
**Duration:** 45 minutes  
**Affected Users:** ~12,000  
**Root Cause:** Lack of deduplication in notification processing

## Summary
On January 15, 2024, between 14:30 and 15:15 UTC, approximately 12,000 users received duplicate push notifications for transaction confirmations. Some users received up to 5 identical notifications within a 5-minute period.

## Timeline
- **14:30:** Payment processing system experiences temporary network partition
- **14:32:** Payment service retries failed notification requests
- **14:35:** Notification cron job runs, processes queued notifications
- **14:36:** Network partition resolves, payment service sends additional notifications
- **14:37-15:15:** Users report receiving multiple identical notifications
- **15:15:** Manual intervention stops notification processing
- **15:30:** Root cause identified and fix deployed

## Impact
- **User Experience:** 1,245 support tickets received
- **App Store Reviews:** 87 negative reviews mentioning "spam notifications"
- **Uninstall Rate:** 0.8% increase in app uninstalls during incident
- **Trust Erosion:** Multiple users reported distrust in transaction confirmations

## Root Cause Analysis
The current cron-based notification system has no mechanism to detect and prevent duplicate notifications. When the payment service experienced a network partition:

1. Initial notification requests failed silently
2. Payment service implemented retry logic (3 retries with exponential backoff)
3. Notification cron job ran and processed the queued requests
4. When network connectivity was restored, retried requests also succeeded
5. No deduplication meant all requests were processed as unique notifications

## Contributing Factors
1. **At-least-once delivery:** System design prioritizes delivery guarantee over deduplication
2. **No idempotency keys:** Notification requests don't include unique idempotency tokens
3. **Retry without coordination:** Services retry independently without global coordination
4. **No consumer state:** Cron jobs are stateless and don't track processed notifications

## Customer Feedback
> "I received the same transaction confirmation 4 times - thought my card was charged multiple times!" - User A

> "Getting spammed with notifications makes me want to turn them off completely" - User B

> "This looks like a bug or security issue" - User C

## Lessons Learned
1. **User perception matters:** Duplicate notifications erode trust more than delayed notifications
2. **Idempotency is critical:** At-least-once systems require deduplication mechanisms
3. **Retry coordination:** Cross-service retry logic needs coordination
4. **Monitoring gaps:** We lacked alerting for duplicate notification patterns

## Action Items
1. [x] Implement short-term fix: Add basic deduplication in cron job (completed)
2. [ ] Design long-term solution: Idempotency keys in notification API
3. [ ] Add monitoring: Alert on duplicate notification patterns
4. [ ] Update documentation: Clarify delivery semantics for service owners

## Recommendations for New System
The replacement notification system should:
- Support idempotency keys for all notification requests
- Implement deduplication at the queue or consumer level
- Provide configurable deduplication windows (recommended: 24 hours)
- Include metrics for duplicate detection rate
- Support both at-least-once and exactly-once delivery semantics based on use case
