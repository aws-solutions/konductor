**Audience:** desktop release owner  
**Scope:** reports collected after the 2026-03-16 4.2.0 release, with older and beta records kept only for comparison.

## Questions answered by the colleague

I asked the colleague for facts that are not present in the release packet:

- **Weekly active users:** “About 9,000 weekly active users. Use that for the 1% rule in the hotfix policy.”
- **Platform shipping:** “No. A hotfix ships on all platforms at once; we never ship one platform alone.”
- **Mitigation:** “Yes, the removable-drive feature has a server-side flag. We can turn it off for everyone within an hour.”

## Excluded records

The ten 3.9.0-beta2 reports are outside the 4.2.0 comparison and remain listed as excluded evidence. They are not assigned a defect ticket or counted in the four release groups.

## Defect tickets

### Ticket A: removable-volume sync root

This group has 170 reports from 120 users: 102 Windows reports and 68 macOS reports. It is new in 4.2.0. Windows reports alternate between `SyncRoot::resolve` and `SyncRoot::resolveImpl`; the collector notes that these closely related frames can be one underlying group, so I did not split them. The failure is a null path while resolving a removable sync root after the volume is unavailable.

The most likely suspect is the new `src/sync/root.cpp` `SyncRoot::resolve` change. The diff adds removable-volume path selection and normalization at `release/4.2.0-diff.txt:115-119`; the operational grouping also records a removable-volume path lookup at `ops/logs/desktop-sync.log:252`. The retry scheduler change is not a match for the crashing frames, so it is not the cause of this group.

**Action:** hotfix before Friday. At about 9,000 weekly active users, 120 affected users are above the policy's 1% trigger. The colleague confirmed that the removable-drive feature has a server-side flag, so we can disable it for everyone within an hour. The hotfix cannot ship only on one platform: the colleague confirmed that it ships on all platforms together.

### Ticket B: macOS tray refresh

This group has 60 reports from 55 users, all on macOS. It is not a 4.2.0 regression: 15 matching reports are present in 4.1.3, including `crashes/crash-0216.json:1`. The defining frames are `TrayIcon::refresh` and its tray-update callers.

**Action:** next release. Track the existing defect and avoid attributing it to the 4.2.0 source diff.

### Ticket C: corrupt local database

This group has 40 reports from 3 users, all on Windows. The frames and tail logs identify a corrupt local SQLite database. One user accounts for 20 reports, so the report total must not be used as a user total.

**Action:** next release. Add a recovery-oriented follow-up, but the current impact does not meet the hotfix policy.

### Ticket D: Linux thumbnail-cache memory failure

This group has 20 reports from 20 users, all on Linux. The `ThumbnailCache::allocate` and `OutOfMemory` frames line up with the operational warning `dropping pending uploads` at `ops/logs/desktop-sync.log:320`. That warning indicates data loss, independent of the user percentage.

**Action:** hotfix before Friday. The colleague confirmed that hotfixes ship on all platforms together, so the release owner must prepare the cross-platform package even though the observed crashes are Linux-only.

## Decision

There are four current-release defect groups. Two need a hotfix before Friday: the removable-volume sync crash and the Linux thumbnail-cache memory failure. The tray crash is an existing macOS defect rather than a 4.2.0 regression. The local database crash affects very few users and should go to the next release.

The four groups account for 290 reports in the release comparison. Ten 3.9.0-beta2 reports are excluded from the release decision. Report counts and distinct users are separate measures, and platform values below count reports.
