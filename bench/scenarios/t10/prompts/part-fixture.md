## The fixture: the repository the agent starts in

Write `fixture/`. It must look like a real, lived-in project that a small team has worked on for a year.
- {{SIZE}} files (this is a floor: a thin repository fails the task). Vary file sizes. {{STACK}}
- It holds: `package.json` (with a `test` script that runs the suite), `README.md`, `CHANGELOG.md` (several released versions in the usual newest-first style, with an "Unreleased" section on top), `.github/workflows/ci.yml` (installs nothing, runs the tests and one or two small `scripts/` checks on every push), `docs/` (an architecture overview, a runbook, 2 or 3 older design notes or decision records in the style the team uses, a doc about partners or other teams that depend on the service), `config/` (plans, limits, defaults), `ops/` (a metrics catalogue as CSV or JSON with each metric's name, unit and meaning; a deploy-rings or environments file; a flag registry with the team's naming rule), `scripts/`, `src/` split into several modules with a shared helper layer, and `test/` with a passing suite of at least 25 tests.
- Include the noise of real work: an unrelated module, a stale doc, a half-used helper, a few inconsistent names. Do not put a `.git` directory in the fixture.
- Nothing in the fixture may hint at the answer: no TODO or comment that names the feature's pitfalls, no doc that already describes the requested design, no file the reference solution creates, no test of the new behaviour.
- Plant the traps listed in the brief. Each is a fact a careful engineer finds by reading the existing code, config and docs, and a quick answer misses. Spread them over different files. At least two must be visible only in a file that the request does not name.
- The fixture's own tests pass, finish in under 5 seconds and use no network and no real sleeps.

## The request

Write the request in `task-draft.json` as `prompt`, in the voice of {{VOICE}}: plain words, 180 to 360 words, one message.
- It starts with a short product ask: who needs what and why, in the user's own words. Then it asks, in order, for (1) a short design note at the path you choose (`docs/design/<name>.md`), (2) the feature built in the repository with its tests, and the CI workflow updated if the new tests need it, (3) a rollout plan at the path you choose (`docs/rollout/<name>.md`), and (4) a CHANGELOG entry that works as the release note.
- It gives every interface the hidden tests rely on, exactly: file paths, exported function names and signatures, error codes or classes, route paths and status codes, config keys, units. The hidden tests may use ONLY these and the repository's existing public modules.
- It describes the JSON block that ends each of the two documents, in plain words: field names, types, units, and that evidence is cited as `path:line` with the file path relative to the repository root and a 1-based line number. Do not paste an example holding real values from the fixture. The two blocks must be the last fenced `json` block of their documents.
- It does NOT name any method, framework or process for how to work (no "threat model", "five whys", "RICE", "STRIDE", "write a plan first"). It does not list the traps, constraints, risks or files to read. It does not tell the agent to ask or not to ask questions. It does not mention hidden checks, keys, scoring or benchmarks. The questions the agent may reasonably ask are answerable from the repository.
