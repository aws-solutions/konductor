# BILL-1187 hand-off (export dates one day late)

Deadline: 2026-11-28, the month-end close. Until the fix ships, billing's month-end totals count some invoices in
the wrong month.

## Steps

1. See the bug. Run `TZ=Pacific/Auckland node --test test/export.test.js`: the INV-3001 line shows 2026-11-01, but
   the invoice was issued on 31 October (UTC). Under `TZ=UTC` the same test passes. That is why CI, which runs in
   UTC, never failed, while the billing export server, which runs in Auckland time, prints the wrong dates.
2. Fix `invoiceDate()` in `src/format-date.js`. It reads the date with local-time methods (`getFullYear`, `getMonth`,
   `getDate`), so the server's zone decides the day. Billing wants the UTC date of the timestamp. This cause comes
   from Sam's investigation and is very likely right, but confirm it with step 1 before you change anything.
   `due_on` is formatted by the same function, so it is wrong the same way and is fixed by the same change.
3. Add a regression test in a new file, `test/format-date.test.js`, that switches the process to a zone east of UTC
   (for example `process.env.TZ = 'Pacific/Auckland'`) and checks `invoiceDate('2026-10-31T13:30:00Z')`. It must
   fail on today's code even when the suite runs with `TZ=UTC`.
4. Run the full suite in both zones, open a pull request from a `fix/BILL-1187-...` branch, and paste the INV-3001
   line before and after.

## Rules you must not break

- The CSV column order is a contract: customers' importers read columns by position. No new, renamed or moved columns.
- `src/legacy/` is frozen (payments team, Ruth Okafor). It slices the ISO string, so it is not affected anyway.
- Nothing goes to `main` directly (see `CONTRIBUTING.md`).
