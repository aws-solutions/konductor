# Harborline webhook relay design

## Purpose and boundaries

Harborline receives normalized events from partner systems, keeps an event history for each customer account, and sends matching events to customer callback URLs. The first hosted release is a single-region service with a stateless HTTP tier, a relational database, and a durable delivery scheduler. Partners do not connect directly to the database or to customer callbacks. The relay owns the common event envelope, delivery state, and operational views. Partner-specific adapters remain outside the relay and turn source-specific messages into the envelope described in `docs/api.md`.

A tenant is the account boundary used for authorization, storage queries, callback selection, and operations views. The sample account identifiers are documentation values. Production account identifiers are generated by the account service and are not meaningful to callers.

The public surface consists of the event receiver and the callback registration APIs. The operations surface contains health, queue, and replay endpoints on a separate private listener. A customer can register more than one callback, and an event type can be sent to every active callback subscribed to that type. The relay does not transform a payload after acceptance.

## Components

**EdgeGateway** is the public ingress proxy. It manages certificates, terminates client TLS, adds the internal request metadata used by the service, and opens a new TLS connection to the private service listener. Only the gateway is advertised in public DNS. The instance security group accepts service traffic from the gateway network and operations traffic from the operations network.

**PublicRateLimiter** runs at the edge and counts requests by source address over a rolling one-minute window. It returns HTTP 429 when the configured window is full. This protects the public listener from a broad burst and gives the operations dashboard a simple request count. The limiter does not inspect event contents.

**InboundReceiver** parses `POST /v1/events`, resolves the partner credentials through `ApiKeyAuthenticator`, and creates a delivery record. It keeps the JSON request body in memory until the request is stored. The common body includes `eventId`, `tenantId`, `type`, `occurredAt`, and `data`. The receiver uses the `tenantId` in that body when it creates the account-scoped event record and when it selects subscriptions. The authenticated account is attached to the request context for logging.

**ApiKeyAuthenticator** looks up the value in the `Authorization` header against the partner-key table. A successful lookup returns a partner id and its account label. Partner keys are provisioned by the operations team through the private admin surface. The key table has one active value per partner in the first release.

**SignatureVerifier** calculates an HMAC-SHA256 digest over the raw body with the partner secret and compares the resulting hexadecimal string with `X-Partner-Signature`. The verification helper is called by the receiver after JSON parsing. The normalized event envelope does not carry a separate freshness field; `occurredAt` is retained as event metadata. `eventId` is used for display and delivery headers.

**EventStore** writes the common envelope, the account label, callback selections, and delivery state to the relational database. QueryLayer is the only module that constructs database statements, and it binds values through the database driver's parameter interface. A stored event includes the complete `data` object so that an operator can inspect a delivery and a customer can reconcile its own history. The current database deployment uses its standard data volume and backup settings.

**CallbackRegistry** saves a display name, callback URL, and event type subscriptions. A callback becomes active as soon as the registration request succeeds. The URL is passed to DeliveryForwarder as the destination string saved in the callback record. Registrations can be updated by the account owner.

**RetryScheduler** reads pending delivery records, places ready records on a shared work queue, and records the next attempt time. DeliveryForwarder makes the callback request and returns the HTTP result to the scheduler. A non-2xx response or transport error increments the attempt count and applies exponential backoff. The default configuration allows eight attempts, and a record can remain pending until an attempt succeeds or the scheduler reaches its configured attempt count. There is one queue for all accounts.

**DeliveryForwarder** sends a POST with the stored JSON payload and an `X-Relay-Event` header. It uses the URL from CallbackRegistry with the platform HTTP client. The client follows normal HTTP redirects and the service does not run a separate destination lookup before connecting. Response bodies are retained briefly for delivery diagnostics.

**AuditLogger** emits JSON lines for request acceptance, authentication results, callback changes, delivery outcomes, and administrator actions. Its request record includes the parsed event and the request headers. At startup it records the partner-key configuration summary used to construct the authenticator. The same logger is used for debug output from the prototype and structured records in the hosted service.

**AdminApi** handles callback support actions, event replay, health checks, and key provisioning. It is guarded by the operations API key in the process configuration. The first deployment has one operations key shared by the small operations group. Admin actions return an operation id that is useful when reading process logs.

## Event flow

A partner sends a normalized JSON envelope to `POST /v1/events`. EdgeGateway checks the source address against PublicRateLimiter, terminates the incoming TLS connection, and forwards the request through a re-encrypted service hop. InboundReceiver parses the body and asks ApiKeyAuthenticator to identify the partner. SignatureVerifier computes the digest and returns a boolean result. On an accepted request, the receiver writes the envelope and a pending delivery record to EventStore, then responds with `202` and the event id.

The receiver asks CallbackRegistry for active subscriptions based on the account label and event type. For each match, it creates a delivery row with attempt one. RetryScheduler sees rows whose next attempt time has arrived and claims them from the shared work queue. DeliveryForwarder posts the stored body to the callback URL. A successful response changes the delivery state to delivered. A timeout, connection error, or non-success status records the response summary and schedules another attempt using the configured backoff. The customer can inspect delivery state through the status endpoint while this happens.

The event endpoint is intentionally asynchronous. A partner receives an acceptance response before callback work completes, and a callback outage therefore does not hold the partner connection open. The scheduler can rebuild its pending view after a process restart from the delivery rows in EventStore.

## Delivery sequence

1. EdgeGateway receives a partner request and applies the public request window.
2. The gateway forwards the body and internal request metadata over the private TLS hop.
3. InboundReceiver parses the body, while ApiKeyAuthenticator resolves the authorization value.
4. SignatureVerifier calculates and compares the HMAC value.
5. EventStore records the event and creates pending delivery rows using the body account label.
6. The service returns `202` with the event id.
7. RetryScheduler claims ready rows from the shared queue.
8. DeliveryForwarder sends the body to each registered destination.
9. EventStore records success or the next attempt time, and AuditLogger writes the outcome.

## Storage and retention

The primary database contains `events`, `callbacks`, `deliveries`, `partner_keys`, and `admin_operations` tables. The event row stores the event id, account label, source partner, type, occurred time, received time, body, and current state. A delivery row stores the callback id, attempt count, last response code, next attempt time, and state. The database has a daily snapshot and point-in-time recovery enabled through the managed service.

Customer history is advertised as thirty days in the account materials. The retention setting is `retentionDays: 30` in the sample configuration. The operations runbook has a monthly storage review and a query for rows older than that setting. Backups follow the managed database's default lifecycle. The design keeps the full body because partial payloads make reconciliation difficult for the first release.

## Operations

The service exposes `/admin/health` for a database check, process version, and queue depth. The queue depth dashboard is split into ready and delayed rows, while delivery dashboards show success, retry, and terminal failure counts. Operators use `/admin/replay/:eventId` after a customer corrects a callback configuration. Key provisioning and callback changes are performed through AdminApi.

Logs are shipped as JSON lines to the hosted log collector. Request ids link edge records, receiver records, delivery outcomes, and admin operation ids. The service records rejected requests as well as accepted requests so that support can explain a missing event. The sample deployment runs three service instances behind EdgeGateway and uses the managed relational database as the durable coordination point.

The first release is deliberately small. It favors a common envelope, durable delivery rows, a single shared scheduler, and familiar relational queries over a more distributed topology. Capacity testing will use representative event bodies and callback response patterns before customer onboarding. Changes to the event schema, callback behavior, or operations listener are recorded in the decision notes and rolled out behind the existing health check. Before a customer is enabled, support creates the account, provisions its partner key, and confirms at least one callback registration. The onboarding record includes the expected event types and an operations contact. A deployment is considered ready when a synthetic event can be accepted, stored, scheduled, and marked delivered in the staging account. The synthetic account uses the same path as a production account but contains no customer data. Operators retain the request id from that exercise so they can correlate each stage while checking the dashboards.
